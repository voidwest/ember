تجارب بحثية

تجربة Rust واحدة، statically compiled، في كل generation run. تراقب التنفيذ أو تعدّل activation موجودة في مكانها، من دون أن تجعل ember منصة plugins عامة. والعقد غير مستقر عمداً في v0.1.

API تجريبي

واجهة التجارب في Rust غير مستقرة في ember v0.1. هي ليست plugin ABI ديناميكية، ولا تعطي وعد توافق ضمن semver.

يوفّر ember hooks عند حدود دلالية معتمدة داخل generation العادي. تبقى الدلالات العددية الخاصة بكل معمارية ظاهرة، ولا تُنسخ tensors لمجرد تشغيل hook.

لا ينشئ المسار العادي ExperimentRunner. وعند التفعيل يحمل الـ run تنفيذاً واحداً لتجربة مجمّعة مع البرنامج، ويستدعي الـ methods الخاصة بها عند حدود الطبقات والـ logits المعتمدة. الأصل هو observation؛ أما التدخل فيتطلب وصولاً mutable وصريحاً إلى activation موجودة. الغرض هو إظهار أن واجهة الـ hooks تكفي لتجارب فعلية من دون تحويل ember إلى منصة plugins عامة.

01 تجربة واحدة لكل run

لا pipeline ولا registry ولا discovery وقت التشغيل، ولا دلالات لتفاعل عدة تجارب.

02 استعر، لا تنسخ

تستعير الـ contexts الـ metadata. أما TensorAccess فهي view غير مالكة فوق allocation يملكه runtime.

03 المعمارية تبقى ظاهرة

أسماء الـ hooks المشتركة لا تمحو normalization أو RoPE أو ترتيب العمليات الخاص بكل عائلة.

مسؤولية تنفيذ التجربة

الواجهة نفسها لا تفرض سلوك observation-only عبر نظام الأنواع. يقع هذا الضمان على تنفيذ التجربة: استخدام values() يحافظ على التنفيذ، بينما قد يغيّره values_mut() أو zero().

بداية سريعة

ابنِ ember مرة واحدة، ثم استخدم خيار تجربة واحداً مع أمر generation عادي. الأمثلة تفترض أن ملفات النموذج والـ tokenizer موجودة في المجلد الحالي. 

cargo build --release

تنبيهات التجربة وملخصاتها تُكتب إلى stderr. النص المولّد يحافظ على تنسيق stdout الحالي. ولا يمكن جمع الخيارين المدمجين لأن الـ run لا يقبل أكثر من تجربة نشطة.

التجارب المدمجة

activation-stats

يسجل L2 norm والقيمة المطلقة القصوى وfingerprint خفيفة عند كل tensor hook.

observation فقط

تعرض جميع الـ tensor hooks في v0.1 activations من نوع f32. تقرأ activation-stats القيم الموجودة من دون طلب mutable access، وتسجل L2 norm والقيمة المطلقة القصوى وfingerprint خفيفة. وبعد اكتمال generation بنجاح، تكتب السجلات بالترتيب في artifact بصيغة JSON. لا تغيّر logits أو التوكنات المولدة. 

target/release/ember \
  --arch qwen3 \
  --model Qwen3-0.6B-Q8_0.gguf \
  --tokenizer tokenizer-qwen3.json \
  --prompt "The capital of France is" \
  --max-tokens 4 \
  --temperature 0 \
  --activation-stats activation-stats.json

حقول الـ artifact

phase
prefill أو decode
stage
اسم الـ hook الدلالي
layer_index
ترقيمه يبدأ من الصفر؛ الحقل غير موجود عند logits
token range
البداية، وعدد توكنات الإدخال، وطول التسلسل
tensor
shape ثنائي الأبعاد وdtype بقيمة f32
values
L2 norm، والقيمة المطلقة القصوى، والـ fingerprint

يُحسب الـ fingerprint بخوارزمية structured tracing نفسها في ember، باستخدام عينة واحدة كل 64 قيمة. يفيد في تحديد موضع divergence، لكنه ليس إثباتاً تشفيرياً للتطابق. أما حساب الـ norm فيقرأ كل القيم. 

jq '.records[] | select(.stage == "after_layer") |
    {phase, layer_index, sequence_length, l2_norm, fingerprint}' \
  activation-stats.json
التوقيت

الـ observation يحافظ على الناتج العددي، لا على التوقيت. مسح activations وتخزين السجلات يضيفان عملاً؛ لذلك ينبغي قياس هذا الحمل في benchmark منفصل.

zero-layer-output

يصفّر مرحلة دلالية واحدة أثناء prefill، ومرة في كل تقييم decode أحادي التوكن يصل إلى الطبقة المختارة.

intervention

الخيار يأخذ رقم طبقة يبدأ ترقيمه من الصفر ومرحلة دلالية بالصيغة LAYER:STAGE. يتحقق ember من الرقم بعد تحميل النموذج، ويعدل الـ tensor نفسها في مكانها، ويسجل عدد التدخلات. يحدث التدخل مرة في prefill، ثم مرة في كل تقييم decode يصل إلى الطبقة المختارة. 

target/release/ember \
  --arch gemma4 \
  --model models/gemma-4-E2B-it.Q8_0.gguf \
  --tokenizer tokenizer-gemma4.json \
  --prompt "The capital of France is" \
  --max-tokens 8 \
  --temperature 0 \
  --zero-layer-output 4:attention
المرحلة الـ tensor التي تُستبدل بالصفر الموضع
attention مساهمة attention مباشرة قبل residual addition
mlp مساهمة MLP مباشرة قبل residual addition
layer hidden state المكتملة بعد اكتمال كل العمليات الخاصة بعائلة النموذج داخل الطبقة

إذا كان اسم المرحلة غير صالح يفشل الأمر أثناء تحليل CLI. وإذا كان رقم الطبقة خارج نطاق النموذج المحمّل، يعرض الخطأ معرّف النموذج وعائلته والرقم المطلوب والنطاق الصحيح. 

research experiment active: zero-layer-output layer=4 stage=attention; execution will be modified
experiment zero-layer-output: 8 intervention(s) at layer 4 stage attention

قد يعرض الملخص عدة تدخلات في generation run واحد لأن العداد يشمل prefill وكل تقييم decode لاحق يصل إلى الطبقة. ولا يعني الرقم أن التجربة عدّلت عدة طبقات.

الناتج والـ provenance

الواجهة من دون تجربة مع تجربة نشطة
stdout تنسيق النص المولّد الحالي التنسيق نفسه
stderr لا تنبيه خاص بالتجربة تنبيه تفعيل، وملخص عند الاكتمال الناجح
run manifest لا يوجد حقل للتجربة الاسم، والإعدادات، وهل عدّلت التنفيذ
artifact لا يوجد activation-stats يكتب JSON

مع activation-stats يسجل الـ manifest القيمة "modifies_execution": false. أما intervention فيسجل الطبقة والمرحلة، ومعهما "modifies_execution": true. ويظل artifact الخاص بالتجربة ملفاً منفصلاً عن run manifest وعن النص المولّد.

حدود التوافق

الواجهة الحالة ملاحظات
generation عادي لـ LLaMA وQwen3 وGemma 4 مدعوم دعم النموذج لا يعني تلقائياً دعم experiment hooks
generation لـ Qwen2.5 experimental لم تكتمل validation المعمارية والـ tokenizer، ولا يشمله سجل parity المتحقق منه
experiment hooks لـ LLaMA وQwen3 وGemma 4 مدعوم prefill وsingle-token decode عبر الحدود الدلالية نفسها
experiment hooks لـ GPT-2 غير مدمج لا يوجد له مسار experiment hooks في v0.1
استخراج hidden states والـ probes مرفوض مع تجربة نشطة دلالات التمثيل غير معرّفة حتى الآن
layer/logit dumps مرفوض مع تجربة نشطة الواجهات العادية من دون تجربة لم تتغير
أوامر demo وinteractive وbenchmark الفرعية مرفوض مع تجربة نشطة التجارب تستهدف generation العادي حالياً
قيد حالي مهم

التجارب النشطة لا تعمل مع استخراج hidden states أو probes أو layer dumps أو logits dumps. لم يعرّف ember بعد هل ينبغي أن تعرض واجهات الفحص هذه القيم قبل intervention أم بعده.

إضافة تجربة مدمجة

التجارب كود Rust مجمّع داخل ember. أبقِ الإضافة ضيقة، ولا توسّع الإطار لخدمة تنفيذ واحد.

  1. أضف تنفيذ التجربة داخل src/experiments/.
  2. طبّق Experiment، واترك الـ hooks غير المستخدمة على defaults الخاصة بها.
  3. أبقِ state والسجلات الخاصة بالتجربة داخل تنفيذها.
  4. استخدم TensorAccess فقط عند tensor hook معتمد.
  5. أضف خيار CLI واحداً وضيّقاً ومحدد النوع، مع مسار إنشاء صريح.
  6. مرّر الأخطاء عبر ExperimentError.
  7. أضف تغطية لترتيب الـ hooks، ودلالات التدخل، والعائلات، والـ parity، والـ allocations، والـ benchmarks.

اقرأ عقد الـ hooks قبل اختيار موضع الإدخال. العقد يوثق ملكية tensors والدلالات الخاصة بكل عائلة وحقول الـ context وmetadata عند الفشل والمسار المعطّل.

ما لا يستهدفه v0.1

النطاق ضيق عمداً. لا توجد plugins ديناميكية بصيغة .so أو .dll، ولا WASM hooks، ولا Python bindings، ولا discovery وقت التشغيل. كذلك لا توجد عدة تجارب متزامنة أو async hooks أو event bus عامة أو إمكانية لتعديل الأوزان اعتباطياً أو tokenizers وexecution backends مخصصة. ولا يقدّم الإصدار ادعاءً واسعاً عن ملاءمته لـ production inference.
