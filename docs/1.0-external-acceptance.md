# External acceptance for the 1.0 candidate

Status: preparation only. No external acceptance is recorded here. Before
issuing this checklist, the maintainer must supply a fetchable candidate commit
and the intended platform/build route. The current uncommitted development tree
is not an independently fetchable release candidate.

The tester must be a person other than the author, using a clean environment
and the published instructions. Record assistance and undocumented steps;
successful runs that depended on them identify documentation work to finish.
Do not copy the author's credentials, model cache, or private USB files.

## Record the environment and candidate

Record the candidate commit, whether the checkout is clean, OS/version, CPU,
RAM, Rust/Cargo versions, Python version, and GUI or headless route. Retain the
commands and their exit codes, including failures. Redact account credentials
and private paths before sharing evidence.

From the candidate checkout:

```sh
git rev-parse HEAD
git status --short
rustc --version --verbose
cargo --version
python3 --version
```

Follow the [README](../README.md) and [GUI installation notes](v06-gui.md).
The current default GUI toolchain is pinned in `rust-toolchain.toml`.
The separately supported headless build is:

```sh
cargo +1.92.0 build --locked --release --no-default-features
```

For the GUI route, build with `cargo build --locked --release`. If testing
both routes, retain each binary and build transcript separately; a later build
can replace `target/release/ember`. Record which binary each result used.

## Obtain the pinned example inputs

Follow the [morphology example instructions](../examples/experiments/README.md)
for the exact model and tokenizer identities. Obtain any required access using
the tester's own authorized account. An access denial is a recorded failure
to complete setup; do not substitute another tokenizer or change expected hashes
to continue. Model weights and authentication tokens are not report attachments.

Run from the repository root with the named files present there. The example
runner checks their hashes before inference. This model is the example Q8_0
pin, not a similarly named file from the Q4/Q6 golden ladder.

## Complete the experiment

First follow the manual example commands: validate, baseline run, inspect,
verify, intervention, compare, restoration, and reproduction. Record confusing
instructions as well as errors. Use a fresh checkout/output location so existing
bundles do not trigger the intentional no-overwrite behavior.

Then collect machine-readable evidence in a new, nonexistent directory:

```sh
python3 scripts/validate_morphology_example.py \
  --ember target/release/ember \
  --workdir /absolute/path/to/new-acceptance-run
```

The script requires Python 3.11 or newer and uses only its standard library. It preserves commands, reports,
and stderr; checks deep bundle verification, an observable intervention, exact
restoration of the 32 captures and generated outputs, and baseline reproduction.
An exit of zero is evidence for that workflow, not every 1.0 release gate or
cross-machine bit identity. Keep the report's actual reproduction verdict.

For the GUI route, also complete the same workflow in the native console.
Record Arabic and Latin editing, keyboard navigation, capture inspection,
comparison/restoration, light/dark appearance, loading guards, and recovery
from an invalid path. Consult the [GUI workflow](v06-gui.md); report features
that cannot be completed rather than substituting a CLI result for a GUI check.
