# M1 performance gate investigation

Gate H remains open. It requires no more than a 3% regression in median decode
throughput or peak RSS against the final v0.4 release on the same hardware and
protocol, together with capture overhead, allocation, compressed residency,
Q8 routing, and binary-size evidence. Old Intel measurements cannot establish
this gate on an M1 Pro.

## Baseline portability

The local `v0.4.0` tag resolves to
`0be7089454c5400f52420bafb1cd02d037811d92`. Its unmodified source does not build
on aarch64 with Rust 1.98.1: seven calls to `is_aarch64_feature_detected!` lack
the macro import. A separate detached checkout at
`/Users/west/Projects/ember-v04-performance` adds only:

```rust
#[cfg(target_arch = "aarch64")]
use std::arch::is_aarch64_feature_detected;
```

That adapted baseline builds with its original lockfile using
`cargo +1.98.1 build --locked --release`. No kernel algorithm is ported from the
candidate. Comparisons must say **adapted v0.4 baseline**, not unmodified tag.
The original failure, complete patch, build log and executable hash are retained.
This establishes a measurable local baseline; it is not a claim of a historical
stock ARM release passing its own validation suite.

## Initial protocol

Before observing timings, the first subset was fixed to the same Llama-3.2-1B
Q8_0 file, `reference` execution, token ID 1, four Rayon threads, 128 single-token
evaluations per repetition, two warmups and five measured repetitions. Four
processes run serially in baseline/candidate/candidate/baseline order. Peak RSS
comes from macOS `/usr/bin/time -l` in bytes. The reported aggregate is the
median of the two per-process throughput medians and the maximum process peak
RSS for each binary. Raw repetitions remain available; this subset alone is
insufficient to resolve noise near the 3% boundary.

Local task evidence lives under `work/1.0-milestones/performance-v04-m1` and
includes the predeclared protocol, commands, model/binary hashes, hardware and
compiler information, working-tree patch/status, raw benchmark JSON, and time
reports. The candidate is an uncommitted development build, not a frozen release
candidate. Its default GUI-linked binary is compared with the original CLI
baseline; binary size is recorded separately and not treated as RSS.

## Remaining gate work

The full gate still needs Q4_K/Q6_K and thread-count coverage, selected/full
capture costs, steady-state allocation checks, compressed residency and Q8
routing checks, a final candidate identity, and a reviewed treatment of the ARM
baseline portability defect. Throughput improvements do not waive memory or
numerical requirements. No threshold is changed based on the result.

## Historical benchmark provenance caveat

The v0.4 benchmark obtains its top-level `git_commit` at runtime from the current
working directory. The comparison driver runs both executables from the candidate
checkout with absolute model paths, so the historical JSON field reports that
checkout's HEAD, not the baseline source commit. Preserve the raw JSON; use the
separately recorded baseline tag/patch and binary SHA-256 for executable identity.
The historical `run_metadata` also reports several macOS fields as `unknown` or
zero; `hardware.txt` records the actual host/compiler information separately.
These fields must not be mistaken for evidence that both binaries are identical
or that the host has zero cores.

## Allocation accounting correction and open failure

A subsequent planned Q4_K_M check exposed two benchmark defects. Global byte
counts subtracted live-memory snapshots, hiding transient allocation traffic;
and measurement vectors grew inside the measured loop. Nested allocation report
schema 3 uses a separate monotonically increasing requested-byte counter and
preallocated sample vectors. The live-byte API remains unchanged. Analysis
retains old schema 1/2 figures under a legacy label instead of treating them as
requested bytes. Counter/report tests and Clippy pass; the default release binary
was rebuilt. The additional counter changes the executable, so the preceding
throughput comparison remains evidence for its recorded binary only.

With 16 evaluations, one warmup and three repetitions on the pinned Llama
Q4_K_M model, the corrected report shows:

| Rayon threads | Caller allocation events | Global events | Global requested bytes |
|---|---:|---:|---:|
| 1 | 0 | 0 | 0 |
| 4 | 90 | 90 | 136,800 |
| 10 | 90 | 90 | 136,800 |

All cases retain 799,592,448 compressed K bytes, zero expanded K bytes and zero
fallbacks. These are allocation diagnostics, not performance timing trials.
Multi-thread steady-state allocation freedom is **not established**: this
measured workload fails it and requires investigation. The earlier apparent
single-thread global allocations were measurement-buffer allocations; the
multi-thread allocations persist after removing that contamination.
Evidence and the new executable identity are in `allocation-accounting-m1`.

## Allocation root cause (2026-09-27)

A temporary, one-shot allocator backtrace captured the first measured 1,520-byte
allocation. Its stack is `CountingAllocator::alloc_zeroed` ->
`crossbeam_deque::Injector<JobRef>::push` -> Rayon's
`Registry::in_worker_cold` -> `k_quant_matmul::parallel_body::recurse` -> planned
linear/decode execution. An external calling thread enters `rayon::join` for
quantized projections; the injector periodically allocates queue blocks. This
happens without another competing workload and is distinct from logits or
capture allocation. Raw diagnostic evidence is in `allocation-trace-m1`.
Diagnostic allocations/timings are not benchmark results. The temporary code
was removed byte-for-byte against its saved pre-trace source, and the normal
release binary rebuilt.

Two existing real-model tests had misleading zero/allocation-free names despite
allowing scheduler allocations. They now describe their existing bounds; the
two-decode test checks both samples instead of only the first. The bounds are
unchanged. On the real Q4 model with four threads they pass with `[5, 5]`
allocations on the allocating route and `2` on the reused-buffer route. These
checks establish neither zero allocation nor a bound over a long decode stream.
The longer measured release workload remains failing.

The execution design must avoid repeated external-thread injection while
preserving parallel work and output semantics. Merely moving benchmark timing
inside a worker or excluding scheduler allocations from counting would not fix
ordinary inference and would not satisfy the gate. No such workaround is applied.

## Production CPU sessions and zero-allocation matrix

Ordinary non-GUI CLI commands now enter `model::with_cpu_session` once around
command execution, including generation and decode benchmarks. Nested sessions
reuse their current Rayon pool. GUI event loops stay on their owning thread;
prepared experiment execution enters a pool with the spec's requested thread
count, using an exclusive mutable session borrow because the model's decode
state is not `Sync`. CLI experiment runs already inside the correct pool avoid
another pool. No unsafe thread-safety implementation, permanent parked worker,
or scheduler-count exclusion was introduced.

This moves the production inference loop, not just its benchmark timer, inside
the worker context and avoids repeated external injector submissions. Session
entry and model preparation remain outside steady-state decode measurements.
Raw low-level forward calls outside a CPU session remain supported and can still
allocate scheduler queue blocks; embedders should wrap complete inference runs
with the experimental helper. This distinction is explicit, not a universal
allocation-free claim for every public Rust call.

On the pinned Llama Q4_K_M and Q6_K rungs, both planned modes at 1, 4, and 10
threads pass the corrected allocation report: all 12 cases record zero caller
and process allocation events/bytes over 64 evaluations × 3 measured repetitions
per case, after one warmup. Compressed residency remains intact with no expanded
K bytes or fallbacks. Evidence: `cpu-session-m1` with commands, raw reports and
executable hash. These runs establish the tested session allocation gate, not
the remaining throughput/memory/capture-overhead portions of Gate H.

Separate real-model tests for Q4 and Q6 compare each logit's bits against an
external-caller run over 64 steady-state evaluations while asserting zero caller
and global allocations. Both pass. Nested custom pools, concurrent callers, and
panic propagation pass helper tests; 78 CLI tests pass (one real-model test
ignored in that general run). The explicit real-model GUI worker restoration
test passes, headless all-target checking and Clippy pass, and a real CLI SIGINT
after prompt encoding exits with code 4. This does not resolve the independent
Q6 compressed-versus-eager numerical discrepancy.

## Current K-quant comparison protocol

The post-session candidate is being compared with the same adapted v0.4 baseline
using `scripts/performance/compare_releases.py`. This matrix covers the pinned
Llama Q4_K_M and Q6_K files, reference/planned/planned-fused execution, and
1/2/4/8 Rayon threads: 24 cells and 96 sequential processes. Each process uses
64 evaluations, one warmup, and three measured repetitions. Each cell uses
baseline/candidate/candidate/baseline order, aggregates the median of the two
process throughput medians and maximum peak RSS, and retains the unchanged 3%
throughput and RSS regression limits.

Unlike the initial Q8 driver, each executable runs from its own checkout so the
historical runtime Git lookup identifies the baseline correctly. The protocol
records binary/model hashes before timing, and the driver rejects a changed
binary before each process. POSIX `wait4` records each child's own peak RSS;
macOS bytes and Linux KiB are normalized to bytes. Raw JSON, stderr, command,
exit status, CPU time and RSS are retained for every process. Source snapshots
and the exact executed driver are retained with the evidence.

Evidence directory: `work/1.0-milestones/k-performance-session-m1`. A partial
`progress.json` is not a matrix verdict: `summary.json` is written only after all
24 cells finish. The matrix was still running when this protocol note was
written, so no throughput or RSS conclusion is asserted here. This comparison
also does not replace capture-overhead measurements, current Q8 routing/timing,
numerical validation, or a frozen release-candidate rerun.

## Selected-row / full-tensor capture overhead (2026-09-28)

`scripts/validate_capture_overhead.py` runs the same v1 experiment three ways on
the pinned Llama Q4_K_M model (reference mode, four threads, 64 generated
tokens, seven repeats): no captures, selected-row captures, and full-tensor
captures at all six hook sites (prefill prompt-final and decode generated-step
1). Captures fire only at those two positions, so this measures the per-capture
cost, not sustained per-token capture:

| Variant | Median wall clock | Decode throughput | Peak RSS | Bundle payload |
| --- | ---: | ---: | ---: | ---: |
| none | 1074.29 ms | 59.57 tok/s | 1,143,177,216 B | 238,516 B |
| selected-rows | 1058.76 ms | 60.45 tok/s | 1,145,618,432 B | 1,386,337 B |
| full-tensor | 1049.08 ms | 61.01 tok/s | 1,145,929,728 B | 1,550,179 B |

Wall-clock and throughput changes are within run-to-run noise (selected-rows
−1.45% / +1.47%; full-tensor −2.35% / +2.40% — all negative-overhead, i.e. no
measurable decode regression). Peak RSS rises ~0.21% (selected) and ~0.24%
(full); the bundle payload grows by 1,147,821 B (selected) and 1,311,663 B
(full), which is the captured data itself. Evidence:
`work/1.0-milestones/candidate-1.0/capture-overhead/summary.json`, with the
per-run specs, bundles, `progress.json`, and binary/model/tokenizer identities.
This closes the Gate H capture-overhead reporting item; it does not claim
per-step capture rates beyond the two tested positions.
