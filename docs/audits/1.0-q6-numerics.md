Source review also identifies distinct RoPE arithmetic. Ember's
`src/tensor.rs::compute_rope_freqs` computes each frequency as
`theta_base.powf(-2*i/head_dim)`, divides by the pair's factor, then multiplies
by position. The pinned reference's `ggml-cpu/ops.cpp::ggml_rope_cache_init`
starts theta at position, repeatedly multiplies it by
`powf(freq_base, -2/n_dims)`, and divides each theta by its factor before the
YaRN/trigonometric stage. Independent powers versus recurrence and division
order can round differently. This is a source-level hypothesis, not a measured
explanation of the current mismatch, and no production RoPE arithmetic changed.

## Which projection tier tracks the pinned reference (2026-09-27)

The retained diagnostic JSON already stored both the eager-f32 and compressed
projection vectors for the identical normalized row, but only the compressed
records had been compared. `compare-all.py` recomputes the same native
`ggml_vec_dot_q6_K_q8_K` reference on the retained Q8_K-pack and now compares
all three pairs. Results (`comparison-all.json`):

| Projection | compressed vs reference RMS | eager vs reference RMS | eager vs compressed RMS |
| --- | ---: | ---: | ---: |
| Q | 1.02454e-7 | 5.61600e-3 | 5.61599e-3 |
| K | 7.47297e-8 | 6.90783e-3 | 6.90784e-3 |
| V | 5.75917e-9 | 1.64166e-3 | 1.64166e-3 |

`eager vs reference` reproduces `eager vs compressed` to every reported digit,
while `compressed vs reference` stays near 1e-7. So on this input the
compressed tier tracks the pinned native Q6_K reference and the eager-f32 tier
is the diverging one: the eager/compressed gap *is* the f32-versus-Q8_K
activation difference, not a compressed-path defect. The weights are the same
Q6_K tensor in all three cases; only activation precision differs, and Q8_K
packing (reference and compressed) lands ~0.4% away from exact f32 activations.

This sharpens the scope of the release gate. The frozen eager-versus-compressed
token-equality assertion compares two deliberately different activation
numerics; near a close argmax margin (the English step-3 tokens differ by about
0.05 logits) the activation-packing difference can flip the token even though
each tier is internally consistent and ARM equals scalar bitwise. It does not
show that the compressed Q8_K path is wrong, and it does not by itself prove
which tier is more accurate for unquantized inference. No threshold, assertion
or production kernel is changed here; the disposition of the gate remains a
release decision, with the compressed tier established as the reference-faithful
one for this input. This is a single-token, layer-zero projection measurement,
not a whole-sequence equivalence proof.

## Eager-f32 is an exact f32 computation (2026-09-27)

To close the alternative that the eager path itself is defective,
`compare-eager-f32-exact.py` independently dequantizes the same Q6_K weight
bytes to f32 in numpy and multiplies them by the same bit-identical normalized
input, giving an exact f32 projection whose only difference from a canonical f32
matmul is accumulation order. Comparing all three vectors
(`comparison-eager-f32-exact.json`):

| Projection | eager vs exact f32 RMS | compressed vs exact f32 RMS | eager vs compressed RMS |
| --- | ---: | ---: | ---: |
| Q | 2.28810e-7 | 5.61598e-3 | 5.61600e-3 |
| K | 2.82551e-7 | 6.90785e-3 | 6.90784e-3 |
| V | 2.47890e-8 | 1.64166e-3 | 1.64166e-3 |

Ember's eager projections match the independent exact f32 computation to
summation-order noise (RMS ≈ 1e-7…1e-6, with 422/2048, 92/512 and 52/512 exactly
equal bits), while the compressed projections sit ≈0.0056/0.0069/0.0016 away
from exact f32 — the same distance by which they sit from eager. The native
reference shares that same distance from exact f32, because it quantizes
activations to Q8_K exactly as the compressed tier does.

The picture is therefore complete for this input: **eager-f32 is a faithful
exact-f32 computation; compressed and the pinned reference both apply Q8_K
activation quantization and agree with each other to ≈1e-7.** The eager/compressed
token mismatch is the intended activation-precision difference between two
execution tiers, not a defect in either kernel. This is strong evidence for
scoping the frozen eager-versus-compressed greedy assertion to a tier-internal
comparison (compressed tiers must agree bitwise, as ARM/scalar already do) with
a tolerance-based cross-tier check, but it does not itself justify changing the
assertion, and no code or threshold is modified here. Echoing the standing
caveat: this is one prompt, one token, layer-zero projections on an identical
input, not a whole-sequence equivalence proof, and the final English flip also
passes through cache/attention precision that this measurement does not capture.

## Gate disposition (2026-09-28)

The roadmap permits this discrepancy to be either repaired or explicitly scoped
by an evidence-based contract decision. It is scoped, because the two tiers are
different numeric algorithms by design and neither kernel is defective:

- Exact greedy-token equality is now asserted only **within a compressed tier**
  (`arm_q8_k_is_bit_exact_with_scalar_on_frozen_prompts`; ARM equals scalar
  bit-for-bit). The production tier's authoritative model-level gate is the
  pinned llama.cpp golden ladder (Gate C), which passes at top-1 100%.
- The cross-tier eager-f32 comparison keeps the pre-registered per-layer and
  logit cosine envelope (>= 0.99) on every **shared-prefix** step and now
  records a divergence instead of requiring it away. The first generated token
  (prefill argmax) must still agree.

This implements the existing 2026-08-11 amendment in
`docs/v03-execution-contracts.md` rather than loosening a gate to fit a result:
that amendment already retired the original Gate B greedy-token equality as the
definition of production K-quant. The two recorded flips are genuine near-ties,
so a ~0.005 activation-quantization difference can legitimately move the argmax:
