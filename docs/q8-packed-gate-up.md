# Q8 packed gate/up benchmark

This note records the evidence for Ember's Gemma 4 packed gate/up dispatch.
The generic row-contiguous Q8_0 path remains the correctness oracle and is
always used while tracing.

## Test system and protocol

- CPU: Intel Core i5-1135G7
- Model: `models/gemma-4-E2B-it.Q8_0.gguf`
- Threads: four Rayon workers pinned to logical CPUs 0-3
- Power profile: `performance` during every timed run, restored to `balanced`
  afterward
- Operator samples: three warmups followed by alternating mode order, nine or
  eleven measured samples per mode
- End-to-end samples: A/B/B/A/A/B process order; each decode process performed
  one warmup and three repetitions of 16 timed tokens

The reproducible operator command is:

```sh
RAYON_NUM_THREADS=4 taskset -c 0-3 cargo bench --bench q8_matmul -- \
  --model models/gemma-4-E2B-it.Q8_0.gguf \
  --layer 0 \
  --rows 1,4,6,8,12,16,24,32 \
  --threads 1,2,4 \
  --cache hot,cold \
  --warmups 3 \
  --samples 9
```

The harness loads the real mmap-backed gate and up tensors, creates
deterministic activations, and requires bit-exact equality between separate,
generic-paired, and packed-paired outputs before collecting timings.

## Operator results

At four threads, median packed-pair speedup over Ember's generic paired path
was:

| Layer shape | Rows | Hot | Cold |
| --- | ---: | ---: | ---: |
| 1536 -> 6144 | 1 | 1.69x | 1.60x |
| 1536 -> 6144 | 4 | 1.53x | 1.38x |
| 1536 -> 6144 | 6 | 1.57x | 1.38x |
| 1536 -> 6144 | 8 | 0.88x | 0.73x |
| 1536 -> 12288 | 1 | 1.91x | 1.71x |
| 1536 -> 12288 | 4 | 1.57x | 1.61x |
| 1536 -> 12288 | 6 | 1.61x | 1.59x |
| 1536 -> 12288 | 8 | 0.91x | 0.80x |

This supports a conservative dispatch boundary: use packed weights for one
row on supported CPUs, and for two through six rows only with at least four
Rayon workers. Eight or more rows stay on the generic tiled batch kernel.

Two scheduling prototypes were rejected:

- A single coarse row-partitioned generic gate/up traversal was about 34-35%
  slower at six rows and 10-15% slower at larger batches. Nested Rayon
  work-stealing kept cores busier than coarse row ownership.
- Running the two packed projections concurrently was 3-10% slower in the
  relevant hot-cache cases. The retained schedule quantizes the shared
  activation once, then gives all workers to gate and up in sequence.

## End-to-end results

For the six-token prompt `The capital of France is`, three alternating process
pairs produced:

| Path | Mean prefill | Derived throughput |
| --- | ---: | ---: |
| Generic oracle | 464.0 ms | 12.93 tok/s |
| Packed gate/up | 343.7 ms | 17.46 tok/s |

That is 25.9% lower prefill latency and 1.35x throughput.

For decode, the mean of three run medians was:

| Path | Decode throughput |
| --- | ---: |
| Generic oracle | 8.54 tok/s |
| Packed gate/up | 10.46 tok/s |

That is a 1.225x decode throughput improvement. A 29-token prompt, which
dispatches to the generic tiled path, averaged 966.0 ms before and 960.3 ms
after; the 0.6% difference is noise-level and shows no fallback regression.

Packing adds about 0.43 seconds to cached model initialization in an
A/B/B/A/A/B run (1.54 seconds generic versus 1.97 seconds packed including one
decode evaluation). The 70 packed gate/up weights contain 1051.875 MiB. Source
mmap pages are evicted as each weight is repacked, so `/usr/bin/time` observed
nearly identical peak RSS for a one-token decode and about 320 MiB higher peak
RSS during the full six-token logits run.

## Correctness and inspectability

- Real-model logits: byte-identical 1.1 MiB NPY artifacts.
- Hidden states: byte-identical layer-dump artifacts.
- Structured tracing: the optimized model deliberately ran the generic path;
  all 529 output fingerprints matched exactly.
- Synthetic focused test: packed and generic gate/up tensors are exactly equal
  for the six-row dispatch regime.
- Long-prompt fallback generated byte-identical output.

The packed representation does not replace or mutate the row-contiguous
weight. Tracing and the benchmark oracle can therefore exercise the original
implementation at any time.

## llama.cpp reference

llama.cpp build 9815 (`0272ac9b1`) on the same pinned four CPUs measured:

| Regime | llama.cpp |
| --- | ---: |
| Six-token prompt | 38.65 tok/s |
| 40-token prompt | 67.56 tok/s |
| 32-token decode | 15.24 tok/s |

llama.cpp remains an external performance reference, not a numerical oracle:
its graph, quantized kernels, and benchmark framing differ from Ember's.
Ember's post-change six-token prefill and decode remain about 2.21x and 1.46x
slower respectively, leaving clear room for future measured work.
