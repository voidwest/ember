# EmberSEC: fuzzing plan

> **Phase I provenance:** frozen audit documentation from branch snapshot
> `e1fe6269`; the measured hardened Ember target is `3ceb7039`. Current main
> retains the applicable hardening, but implementation names and dataflow may
> have evolved. Read this as the published Phase I evidence record.

The `fuzz/corpus/` and `scripts/embersec_gen_fuzz_corpus.py` references below
describe the frozen branch workflow and are retained for provenance; they are
not transplanted to current main. See [`fuzz/README.md`](../../fuzz/README.md)
for the current eight-target fuzz workflow. The complete Phase I comparative
fixtures remain published under `research/embersec/comparative/`.

Repository state: cargo-fuzz is present in the isolated `fuzz/` crate and
is exercised by CI. The crate also retains the proptest safety net in
`tests/property.rs` (`gguf_loader_never_panics` and friends: arbitrary
bytes into `load_gguf_from_reader` must return `Ok` or `Err`, never
panic). This document records the targets, seed corpus, and bounded
execution procedure.

## Goal

```
attacker-controlled GGUF bytes
    -> parser (read_gguf_* + read_tensor_info)
    -> semantic validator (TensorInfo::validate -> ValidatedTensorInfo)
    -> ... (no full inference, no model construction)
```

The loader target stops at the validation boundary: after
`load_gguf_from_reader_impl` returns, all memory-visible state is
validated. The separate `gguf_to_llama` target covers
`Llama::from_loader` and therefore exercises model construction without
mixing its cost into the parser target.

## Ideal first target

`fuzz/fuzz_targets/gguf_loader.rs`:

```rust
#![no_main]
use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    // Both entry points share one implementation; the reader variant is
    // allocation-friendly for fuzzing (no mmap).
    let mut cursor = std::io::Cursor::new(data);
    let _ = ember::loader::load_gguf_from_reader(&mut cursor);
});
```

Plus a second target that drives the validator directly on
synthetically constructed descriptor tables (dims/dtype/offset
combinations), to hit overflow paths without paying string/parse cost:

- dims drawn from {0, 1, 31, 32, 33, 255, 256, 257, 2^32, u64::MAX}
- dtype from {0,1,2,8,9,10..15,30, u32::MAX}
- offsets near {0, file_len, u64::MAX}

## Corpus structure

`fuzz/corpus/gguf_loader/`:

- `valid/` — tiny valid GGUFs: f32, f16, bf16, q8_0, q4_k, q6_k, mixed
  tensors, with/without metadata, alignment 1/32/64/256, tensors at
  exact EOF. Generated once by a small builder script (the
  `build_single_tensor_gguf` pattern from tests/loader_security.rs).
- `malformed/` — the adversarial fixtures from
  tests/loader_security.rs (truncated data, overflow offsets, huge
  counts, bad alignment, overlapping ranges, duplicate names, bad
  rank/dims, unsupported dtypes, deep arrays, huge strings).
- `fuzz/corpus/gguf_loader_seed` notes: libFuzzer will minimize from
  these; keep each file < 4 KiB so mutations stay cheap.

## What the target will find first

Likely categories, in order: (1) panics in asserts reached with
hostile-but-structurally-valid descriptors (e.g. `CpuTensor::from_data`
asserts if any arm miscalculates), (2) `try_reserve`/`with_capacity`
aborts if a count heuristic is ever bypassed, (3) integer-overflow
paths if a future refactor reintroduces unchecked arithmetic. The
validator's error messages should name the violated invariant without
echoing attacker strings (already the loader style).

## Status: cargo-fuzz is live (2026-08)

`fuzz/` is an isolated non-workspace crate (stable CI never touches it):

- `fuzz/fuzz_targets/gguf_loader.rs` — GGUF bytes -> parser -> semantic
  validator (stops before model construction).
- `fuzz/fuzz_targets/gguf_to_llama.rs` — adds `Llama::from_loader` so
  hostile-but-complete files also exercise the model-construction
  boundary (config caps + inventory gate).
- Seeds in `fuzz/corpus/` are generated by
  `scripts/embersec_gen_fuzz_corpus.py` (mirrors the adversarial test
  fixtures, all < 4 KiB) and verified by the
  `fuzz_seed_corpus_behaves_as_intended` test. Run cargo-fuzz against a
  separate working corpus (`fuzz/corpus_work/`, gitignored) so the seed
  corpus stays pristine.
- `fuzz/fuzz_targets/tokenizer_json.rs` — tokenizer.json bytes through
  the EmberTokenizer boundary (size cap + well-formedness gate +
  panic boundary), then encode/decode on anything that parses. Found a
  panic in tokenizers-0.20.4 (`decoders/mod.rs:90 .expect("Helper")`);
  see docs/embersec/tokenizer-boundary.md.
- CI: `.github/workflows/fuzz.yml` (nightly + cargo-fuzz, 180 s per
  target, artifacts uploaded on failure).

First findings (all fixed):

1. `llama.attention.key_length = 1` (odd) passed `config.validate()` and
   panicked in `compute_rope_freqs` ("RoPE head dimension must be
   positive and even") — the crash was minimized by `cargo fuzz tmin`.
   Fix: head dims must be positive AND even in llama/gemma4 config
   validation; gemma4's optional `rope_freqs.weight` length and factor
   values are validated before use (its asserts would otherwise panic).
2. Same class reviewed across the builder: 1-D F32 linear weights would
   panic in `gguf_to_row_major_f32`/`transpose` (2-D asserts); the
   llama/gemma4/gpt2 take helpers now reject them with structured
   errors.

After the fixes, both targets ran 300 s with zero crashes (gguf_loader
~8.9 M execs, gguf_to_llama ~1.1 M execs, peak RSS < 800 MB).
